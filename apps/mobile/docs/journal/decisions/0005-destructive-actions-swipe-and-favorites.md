# ADR 0005 — 파괴적 액션 모델: 스와이프 제스처 + 삭제 의미 + 즐겨찾기

- **날짜**: 2026-08-06
- **스텝**: mobile — 죽은 디자인 살리기(삭제/즐겨찾기)
- **상태**: accepted

## 맥락 (Context)
리스트(Phrases·Library·Sessions·Stories)와 상세(clip player·phrase)에서 삭제 기능이 없었고, 상세 우측 상단 `...` 버튼은 `onPress` 없는 **죽은 UI**였다. 사용자는 (1) 밀어서 삭제, (2) `...` 살리기를 요청했다가, 최종적으로 **`...` UI 자체를 제거하고 스와이프 제스처로 통일**하기로 방향을 바꿨다. 제약: 공유 prod DB(웹과 공용, RLS on), 마이그레이션은 사람이 SQL Editor에서 수동 실행, 삭제는 되돌릴 수 없음.

## 검토한 선택지 (Options)

1. **`...` 오버플로 메뉴(ActionSheetIOS) 중심** — 장점: 항목 여러 개(fav/practice/delete) 담기 쉬움. 단점: 리스트에서 각 행을 열어야 접근, 탭 수 많음. 사용자가 "UI 없애자"로 기각.
2. **스와이프 제스처(좌우 대칭)** — 오른쪽→왼쪽=삭제, 왼쪽→오른쪽=즐겨찾기. 장점: iOS 표준, 한 손 제스처, 상세 진입 불필요. 단점: 발견성 낮음(숨은 액션).
3. **삭제 의미**: (a) 전부 하드 삭제 vs (b) 엔티티별 차등.
4. **즐겨찾기 저장소**: (a) 새 컬럼 마이그레이션 vs (b) 마이그레이션 없이 다른 액션으로 대체.

## 결정 (Decision)
스와이프 제스처로 통일(2)하고 `...`를 제거. 삭제는 **엔티티별 차등**(4b/3b): 클립·표현·세션은 하드 삭제(FK 캐스케이드), **스토리는 소프트 아카이브**. 즐겨찾기는 **additive 마이그레이션(021: videos·bookmarks에 `is_favorite`)**(4a)로 실제 기능화. 파괴적 액션 앞엔 네이티브 확인 다이얼로그(`Alert`, destructive).

## 기각 이유 (판단의 증거)
- **`...` 중심 기각**: 사용자가 명시적으로 UI 제거 요청. 스와이프가 이미 삭제를 커버하니 오버플로 메뉴는 중복.
- **스토리 하드 삭제 기각**: `stories` 삭제는 `messages`·`message_beats`·`talk_sessions`(전부 `ON DELETE CASCADE`)까지 연쇄 삭제 → 대화 기록 손실. 앱은 이미 `status='archived'` 필터(`neq archived`)를 쓰므로 **아카이브가 리스트에서 제거 + 데이터 보존 + 되돌리기 가능**을 동시에 만족. 반면 클립/표현/세션은 캐스케이드가 의도된 정리(클립→세그먼트→북마크)라 하드 삭제가 맞음.
- **마이그레이션 없이 대체 기각**: 사용자가 "제대로 추가" 선택. `is_favorite`는 nullable-default boolean이라 **웹에 무해**(웹은 컬럼별 select), RLS도 기존 owner `FOR ALL` 정책이 UPDATE를 커버 → 새 정책 불필요.

## 결과 (Consequences)
- **감수**: 스와이프 액션은 발견성이 낮다(온보딩·힌트 미제공). 클립 하드 삭제 시 **R2 미디어 오브젝트는 고아로 남음**(모바일→R2 삭제 경로 없음) — 스토리지만 소모, 후속 정리 항목.
- **순서 의존성**: 021을 실행하기 전 앱을 리로드하면 `is_favorite` 부재로 **Library·Phrases 로딩이 통째로 깨진다**(둘 다 컬럼을 select). 마이그레이션 우선.
- **재검토 조건(revisit trigger)**: (1) 사용자가 스와이프 액션을 못 찾는다는 신호 → 시각적 어포던스/힌트 추가, (2) 즐겨찾기가 필터/별표를 넘어 정렬·홈 노출 등으로 커지면 별도 뷰 설계, (3) 고아 R2 오브젝트가 스토리지 비용으로 부각되면 삭제 시 R2 정리 Edge Function 추가.
